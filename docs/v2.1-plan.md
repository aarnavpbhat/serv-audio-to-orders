Step 1: The one failing eval case
Find the failing case, prove which layer caused it, fix it at that layer without special-casing the fixture, and add a test that keeps it fixed.
1. Identify it. Read the latest eval/report.json and the /eval page. Record the fixture or checklist row, which run it failed in (ceiling, real providers, held-out, or a live-path metric), and the exact diff (expected vs got).
2. Isolate the layer. Re-run only that case in each configuration. The first one that fails points at the culprit:
Configuration
If it fails, the bug is in
Script transcriber + oracle events
Our code: tracker, replay(), post-processing, scoring
Script transcriber + Gemini
Extraction: prompt, validation, fuzzy matching
Deepgram + Gemini, replay at max speed
Transcription or role labels
Deepgram + Gemini, replay at 1x
Timing: tracker timers, reconnect or close races
3. Check if it is flaky. Run the failing configuration 3 times. If results differ between runs, record the spread. Flaky causes are usually model variance (even at temperature 0) or a timing race. A race is a bug; model variance needs a sturdier rule, not a lucky rerun.
4. Fix at the right layer.
• No fixture-specific hacks: no if on this fixture's name, phrase or values.
• A prompt change must be re-run on the full eval, and the held-out set reported (never tuned on).
• A rule change from the v2 plan (outcomes, timers) needs Aarnav's approval first.
5. Lock it in. Add a regression test at the lowest layer that reproduces the failure, using cached transcripts and model responses so it runs free and offline.
Done when: the case passes 3 of 3 runs in the configuration that failed; the full eval shows no new failures; docs/investigations/01-eval-failure.md explains the cause in plain language.

Step 4: Stop and cancel live streams
Any live stream (simulator, replay over WebSocket, or a real connection) can be stopped from the UI in one click, and stopping really stops everything: audio, Deepgram, timers and reconnects.
Two actions (E3):
Action
Open conversation
Webhook
Session marked
End session
Finalized now; outcome from evidence (usually undetermined), flag ended_by_operator
Sent
ended
Discard
Dropped, no order created
None
discarded; data kept and excluded from metrics (E4)
Discard asks for confirmation. Both are idempotent: pressing twice, or stopping an already-closed session, does nothing and shows no error.
Where the buttons live:
• In the simulator and lane view: a Stop control always visible while live, with both actions.
• A Sessions panel listing every active session (store, lane, source, duration, Deepgram minutes) with the same two actions per row.
• Queued or running replays and runs get a Cancel button too.
Server: POST /api/sessions/:id/stop with { mode: "end" | "discard" } (dev routes and localhost only, like the simulator). In order: mark the session stopping so no reconnect is accepted for it; close the client socket with code 4000 "stopped by operator"; close the Deepgram connection; kill the session's ffmpeg process; cancel tracker timers; flush the raw capture part; apply the mode to the open conversation; free the lane.
Browser: on stop, call track.stop() on every mic track, close the AudioContext, and turn off auto-reconnect. Without that last step the reconnect logic restarts the stream the user just stopped.
Tests: stop mid-conversation in both modes; stop during reconnect backoff; stop twice; stop from a second tab; Deepgram minutes stop increasing within 2 s; no webhook after Discard; the lane accepts a new connection right after.
Done when: all tests pass and a stopped session never comes back by itself.

Step 6: Review page, narrowed scope
The review page exists for one job: a person resolves orders the system flagged as uncertain, when nobody knows the right answer except by listening. It should show only those orders and give the reviewer the audio they need to decide.
What is wrong today:
• It lists every order, including completed orders with no flags, which need nothing from a person.
• It asks for human review on synthetic fixtures, where the script already says what was ordered (and where unclear items are deliberate mistakes, so a listener cannot tell what was meant).
• The reviewer cannot hear the part of the audio that caused the flag.
New scope (E5, E6):
Run type
Ground truth?
What the user sees
Fixture replay, scripted Test Lab run
Yes (the script)
No review. An automatic Expected vs extracted panel on the run page
Free-play Test Lab, phone recordings, real HME audio
No
Flagged orders go to the Review queue
Review queue:
• Only orders with review.required = true, any status, newest first. A badge in the nav shows the count.
• A separate read-only Orders page lists all orders with filters (status, review, store, lane, date). That is where completed orders live.
• Each item shows: why it was flagged, in plain words ("We heard a shake but not which flavor"); an audio clip of exactly the flagged lines, from the archive, with 2 seconds before and after; those transcript lines; the top menu candidates; and the current order.
• Actions: pick a candidate, mark as not ordered, change quantity, or confirm the outcome. Save sends order.updated as the next version. Looks right clears the flag with a note and also sends order.updated (the review flag changed).
Expected vs extracted panel (reused by Test Lab's scorecard): items, outcome and flags side by side, with every difference highlighted and labeled with where it came from (see step 7's attribution).
Done when: a completed, unflagged order never appears in the queue; fixture runs show the diff panel and no review prompt; the audio clip plays the flagged lines; saving shows the new version in the mock inbox.
Step 7: Test Lab
Replace the simulator's wall of controls with a guided flow: pick a scenario, follow a script on screen, and get a scorecard that says whether the system got it right and, if not, which part failed.
The flow: Setup → Pick a test → Run → Scorecard → Results history. The page is renamed Test Lab.
1. Setup (one screen, remembered next time):
• Mic check: a level meter and "Say something"; it turns green when speech is detected. Fixes permission and sample-rate problems before a test starts.
• Who is testing (E7):
    ◦ Just me, both parts: you read every line; the script shows whose turn it is.
    ◦ Just me, robot crew: the app speaks the crew lines aloud through the laptop speaker and you answer as the customer. Turn off browser echo cancellation for this mode so the crew voice reaches the mic, like a real headset mix.
    ◦ Two people: one plays crew, one plays customer, both near the same laptop. A short card explains where to sit and to speak at a normal volume.
• Typing instead of speaking (free, no Deepgram) stays available under Advanced.
2. Pick a test. Each scenario is a card with what it checks and how long it takes:

3. Run screen:
• A large teleprompter: the current line, who says it ("CUSTOMER" or "CREW" in distinct colors), and the next line in preview.
• The script advances when the transcript finalizes a line from the expected speaker; Space or a Next button advances manually.
• The app performs the scenario's actions itself (car arrived, drop connection) and shows a banner ("Simulating a dropped connection, reconnecting in 4 s"). No manual event buttons in guided mode.
• Beside the script: the live transcript, the order building, and a status chip in plain words: Waiting for a car, Ordering, Wrapping up, Order sent.
• Stop (End or Discard, from step 4) is always visible. Manual event buttons and fault controls live in a collapsed Advanced drawer.
4. Scorecard (after each run):
• Pass or fail headline, then the Expected vs extracted panel from step 6.
• Where it went wrong: for each difference, re-run extraction on the script's exact words (a perfect transcript). If that version is right, the miss is labeled heard wrong (transcription); if it is also wrong, understood wrong (extraction); if the order was split or closed at the wrong time, timing (tracker).
• Transcript accuracy: word error rate against the script, per role.
• Role accuracy: share of lines labeled with the right speaker.
• Speed: conversation end to order sent.
• Buttons: Retry, Next test, Save as fixture, and Save as held-out.
5. Results history: pass rate per scenario, word error rate, role accuracy and speed over time, filterable by tester mode and model version. This is where Aarnav sees model performance at a glance.
Free play: the same run screen with no script. When it ends, a menu picker asks "What was actually ordered?" That answer becomes the ground truth, the run is scored, and it can be saved as a fixture or held-out case. Without an answer, flagged orders go to the review queue.
Done when: Aarnav completes "Simple order" using only what is on screen; all 10 scenarios run in every tester mode; a deliberately wrong run (skip a line) produces a fail with the correct attribution; the history page aggregates at least 3 runs.
