1The process on one page

v1 took a finished MP3 and turned it into orders. v2 and v2.1 turn the same logic into a live service: an HME base station streams each lane's audio over a WebSocket while cars are ordering, and each finished conversation becomes a webhook within seconds. Files still work: they are replayed into the same lane as if they were live, so there is one path, not two.

The seven steps in plain words

  1. Connect. The base station opens /hme/v1/stream on our feed service with a per-store bearer token, and names its lane and audio format (codec, sample rate, channels). Bad tokens, unknown lanes and bad formats are refused before the socket opens.
  2. Decode. Binary messages are audio; text messages are JSON events such as vehicle_arrived. Every message is saved raw first (so any session can be replayed byte for byte later), then audio is decoded to 16 kHz PCM and timed by our receive clock.
  3. Transcribe. Each lane has its own Deepgram live connection (Nova-3). Only final results become utterances; interim words go to the screen. Speaker roles come from separate channels if HME provides them, otherwise from diarization and wording.
  4. Track. A per-lane state machine (IDLE → ACTIVE → CLOSING → FINALIZED) decides where one car's conversation starts and ends, using spoken cues ("welcome", "pull forward"), vehicle events and timers. It can reopen an order for 20 s if the customer adds something late.
  5. Extract. One Gemini call per finished conversation. The model returns events (ADD, REPLACE, CHANGE_QTY, CANCEL_ORDER, READBACK...) that point at catalog IDs. It never writes the order itself.
  6. Build. The pure function replay(events) applies the events to produce the order. Post-processing sorts every mention into items, needs review or not ordered, finds combo savings, sets the outcome from evidence, and decides whether a person should check it.
  7. Deliver. The payload is written to an SQLite outbox and POSTed at once to WEBHOOK_URL, signed per the Standard Webhooks spec. Failures retry for about a day before going to a dead letter queue you can resend from.
The core ruleThe LLM proposes, code decides. Gemini can be wrong about what it heard, but it cannot invent a menu item, a price or a total: those come from the catalog and from code that is unit-tested. Corrections, cancellations and readbacks are deterministic.

Where it runs

Feed service: pnpm feed serve

The live part. Listens on 127.0.0.1:8787, runs one lane per store and lane, talks to Deepgram and Gemini, writes orders, and delivers webhooks. Everything it keeps goes under .data/.

Web app: pnpm dev

Next.js on localhost:3000. Shows runs, orders, Test Lab, the eval, and the mock webhook receiver. Reads the same SQLite database the feed service writes. Also runs file uploads and the slow-phase retry worker.

When there is no closing cue

The tracker never guesses that a car left from a pause alone (plan decision D10). Without a closing cue, a conversation finalizes when the next car starts, after 45 s of silence (IDLE_TIMEOUT_S), when a vehicle_departed event arrives, or at the 6 minute cap. That is why the 95th percentile close time is about 45 s: those orders wait for the idle timer. HME vehicle events would shorten that tail.

When the connection drops

The lane survives reconnects. An open conversation is held for 180 s (RECONNECT_GRACE_S). If the base station comes back, the order continues and is flagged stream_gap (which also asks for review). If not, it is finalized with stream_interrupted. A dropped connection never decides the outcome by itself.

Your question: do we connect to HME's WebSocket?

Possibly, but the code assumes the opposite direction, and that is worth confirming with HME first.

What the code assumes now

HME connects to us. We run the WebSocket server; each base station dials out to our URL. This matches HME's installation guide, which only asks the installer for a provider URL and port: that is the shape of a device that pushes to a provider, not one that waits to be called. It is also easier for stores: no inbound firewall holes at each restaurant.

If HME exposes a socket instead

We connect to HME. Then we add a small WebSocket client per lane in src/input/hme/ that dials HME, reconnects with backoff, and feeds the same HmeConnection class. Everything from decoding onward is unchanged. Our server-side token check would be replaced by whatever credentials HME gives us.

Either way, the questions for HME are the same:

  1. Who opens the connection, and to what URL? One connection per lane, or per store with lanes multiplexed?
  2. Audio format: codec, sample rate, mono or a separate crew and customer channel? (Separate channels make speaker roles nearly free and much more accurate.)
  3. Does the stream send vehicle-detection events (car at the speaker post, car left)? With what message format and timestamps?
  4. Does audio stop when no car is present? (The code handles both: a burst after a pause is placed by its own arrival time.)
  5. Authentication: tokens, client certificates, IP ranges?
  6. Reconnect behaviour and keepalives. (The simulator assumes HME retries at 2, 4 and 8 s.)

Nothing has been tested against a real base station yet. The raw capture of every message means the first real session can be replayed through the pipeline as often as needed (pnpm feed replay-raw) once we have one.

6Outcomes, including abandoned

Yes, abandoned orders are sent, like every other outcome. The status answers one question, "how did this conversation end?", and is set only from evidence. Whether a person should check the order is a separate question, answered by review, which can be true on any status.

StatusSet whenExample evidence
completedA crew closing cue ("pull forward", "see you at the window") or the customer's "that's it" acknowledged by the crew, after at least one itemspoken_cue / closing / "pull forward"
cancelledThe customer cancelled the whole orderspoken_cue / cancel, or order_state / all_items_removed
abandonedThe car left before a completion: a vehicle_departed event, the crew saying so ("they drove off"), or the next car's vehicle_arrivedvehicle_event / vehicle_departed
undeterminedNo evidence either way (for example, the audio stops with no cue and no vehicle event)Only context_only entries
Why pauses do not decideA pause, silence or a dropped connection is recorded as context_only evidence and never sets completed or abandoned by itself (plan decision D10). A crew member can step away mid-order; a connection can drop while the car is still there. Guessing would send confident but wrong outcomes.

Gap found while writing this: a greeted car that drives off silently is not sent

Checked on October 6 with a throwaway lane test: vehicle_arrived, the crew's "Welcome, what can I get for you?", vehicle_departed gives no order. A car that left without anyone speaking is sent (E1). The cause is in lane/lane.ts (runFinalize): a conversation with no customer speech is dropped, and the E1 exception only applies when there was no speech at all. From Serv's point of view the greeted car is the more interesting abandoned visit (someone was at the post and left), so it should be sent like E1: abandoned, no items, no_speech (or a new no_customer_speech flag), no review, no Gemini call.

This is a small change plus a lane test, and it needs your decision (call it E13) since it changes what Serv receives. Without vehicle events, nothing changes: a greeting with no customer and no departure still sends nothing.

Without vehicle events

If HME does not send vehicle events, abandonment can only come from what is said ("they left", or the crew greeting a new car mid-order together with an arrival). Otherwise the visit ends undetermined: still sent, with items and times, so Serv can match it to the POS. Vehicle events are the single biggest improvement for outcomes, which is why they are on the list of questions for HME.

7How duplicates are prevented

Webhooks are at least once by nature: if Serv processes an order but its response is lost (a timeout, a dropped connection), we cannot tell the difference from a failure and must retry. So the guarantee is built in two halves: we never create a second identity for the same order version, and the receiver ignores a version it has already seen.

Our side (the sender)

MechanismWhat it prevents
One order_id per car, minted when the conversation opensA reopen, late evidence or a human correction becomes version 2 of the same order, never a new order.
webhook-id = {order_id}_v{version}Retries of one version carry the same ID; each version has its own. The receiver needs no other key.
Outbox primary key on webhook_id, insert-or-ignoreEnqueueing the same version twice (a restart, a double finalize) is a no-op.
Orders table primary key (order_id, version)A version is stored once.
Atomic claim (status pending → delivering)The inline sender and the retry worker can never send the same row at the same moment.
Frozen bodyEvery retry sends byte-identical JSON; only the timestamp and signature headers are new.
Version orderingVersion N waits until N-1 is delivered, failed or dead, so order.updated never arrives before the order.finalized it corrects.
Stuck-row recoveryWhen the worker starts after a crash, rows left delivering for over 2 minutes go back to pending. They may be sent again, which is exactly what receiver dedupe absorbs.
Eval checkpnpm eval counts duplicate versions and premature reopens on every fixture; checklist rows 27 and 28 run a signed delivery and a duplicate against the mock receiver.

Serv's side (the receiver): two rules

1. Dedupe on webhook-id

If you have already accepted this ID, answer 200 and do nothing. Never answer 4xx or 5xx to a duplicate, or we will keep retrying.

2. Keep the highest version

Store per order_id. Accept a version only if it is higher than the one held; an older or equal one is a duplicate. One conditional write does both rules (section 8).

The sandbox's mock receiver (webhook/mock-receiver.ts) does exactly this, and you can watch it on /mock-webhook: send an order, use Resend, and the second arrival shows as duplicate.

What can still produce a second order for the same car

CaseWhat to do
The tracker splits one car into two conversations (a long pause mid-order read as a new car)A segmentation error, not a delivery bug: two order_ids. Measured by the eval (74 of 74 fixture conversations found, none extra). Real audio may differ.
Someone replays a captured session or re-runs a file into the same webhookMints new order_ids by design (it is a new run). Point replays at the mock, not at Serv. If needed, Serv can add a soft check on store_id + lane_id + times.started_at.
A split bill (group_id set)Not a duplicate: two real orders from one car, linked by group_id.
The feed service restarts mid-conversationThe open conversation is lost, not duplicated (lane state is in memory). Already-built orders are safe in the outbox. In production, run one owner per lane and drain on deploy.

8Receiving the webhook on AWS Lambda

Nothing changes on our side except two settings: WEBHOOK_URL (the Lambda's URL) and WEBHOOK_SECRET (a whsec_... secret both sides share). The work is on the receiving side.

Steps

  1. Generate a secret in the whsec_<base64> form (our generateSecret() makes one) and store it in Secrets Manager. Give the same value to the feed service as WEBHOOK_SECRET.
  2. Create a DynamoDB table orders with partition key order_id (string). On-demand billing is fine.
  3. Create the Lambda (Node.js 22, 256 MB, 10 s timeout) with the handler below and the standardwebhooks npm package. Give its role dynamodb:PutItem on the table and read access to the secret.
  4. Expose it with a Lambda Function URL (auth type NONE: the signature is the authentication) or an API Gateway HTTP API route POST /serv/orders, if Serv wants WAF, throttling or a custom domain.
  5. Point the feed service at it: WEBHOOK_URL=https://.... Check with pnpm pipeline settings, then send a fixture: pnpm pipeline run fixtures/audio/... and watch the deliveries panel on the run page.
  6. Test failure paths: Resend an order (expect 200 and no new row), and make the Lambda return 500 once (we retry with backoff, then the order lands).

The handler

// index.mjs  (Node.js 22, ESM). npm i standardwebhooks @aws-sdk/client-dynamodb
import { Webhook } from "standardwebhooks";
import { DynamoDBClient, PutItemCommand, ConditionalCheckFailedException } from "@aws-sdk/client-dynamodb";

const db = new DynamoDBClient({});
const wh = new Webhook(process.env.WEBHOOK_SECRET);   // whsec_... (load from Secrets Manager in prod)

export const handler = async (event) => {
  // Verify against the exact bytes we sent; never re-serialize the JSON first.
  const body = event.isBase64Encoded ? Buffer.from(event.body, "base64").toString("utf8") : event.body;
  let order;
  try {
    order = wh.verify(body, event.headers);            // checks signature + 5 min timestamp window
  } catch {
    return { statusCode: 401, body: "bad signature" };  // 4xx: we will not retry
  }

  try {
    // One conditional write = dedupe on webhook-id AND keep the highest version.
    await db.send(new PutItemCommand({
      TableName: "orders",
      Item: {
        order_id:      { S: order.order_id },
        order_version: { N: String(order.order_version) },
        webhook_id:    { S: event.headers["webhook-id"] },
        status:        { S: order.status },
        store_id:      { S: order.store_id },
        lane_id:       { S: order.lane_id },
        payload:       { S: body },
      },
      ConditionExpression: "attribute_not_exists(order_id) OR order_version < :v",
      ExpressionAttributeValues: { ":v": { N: String(order.order_version) } },
    }));
  } catch (e) {
    if (e instanceof ConditionalCheckFailedException) {
      return { statusCode: 200, body: '{"duplicate":true}' };   // same or older version: already have it
    }
    throw e;  // an unhandled error gives a 5xx: we retry
  }
  return { statusCode: 200, body: '{"received":true}' };
};

Rules that matter

  • Answer fast. We time out after 10 s and retry. Store the payload and return 200; do POS matching or anything slow downstream (DynamoDB Streams, or SQS FIFO with MessageDeduplicationId = webhook-id).
  • Status codes steer our retries. Any 2xx is success. 408, 429 and 5xx (and timeouts) are retried, honoring Retry-After: about 1, 2, 4, 8, 16, 32 s, then 5 min, 30 min, 2 h, 5 h, 10 h, 10 h, then dead letter. Any other 4xx is treated as permanent: return 401 only for a bad signature, and 400 only for a body you can never accept.
  • Verify the raw body. API Gateway and Function URLs pass the body through as a string; parsing and re-stringifying it before verifying will break the signature.
  • Lowercase headers. Both Function URLs and HTTP APIs deliver them lowercased, which is what the library expects.
  • Secret rotation. The signature header may hold two signatures (space-separated) while a new secret rolls out; the library accepts either.
  • Could the feed service itself run on Lambda? No: it holds long-lived WebSockets and per-lane state for hours. It belongs on a container (ECS Fargate) with the outbox in Postgres. Only the receiver fits Lambda well.

Glossary

Base stationHME's box at the restaurant that carries the headset audio. It would stream to us. LaneOne drive-thru lane; one audio stream, one tracker, one order at a time. SessionOne WebSocket connection. A lane outlives its sessions (reconnects). ConversationOne car's exchange at the speaker post; becomes one order (or several, for a split bill). TrackerThe per-lane state machine that decides when a conversation starts and ends. EventWhat the LLM returns: ADD, REPLACE, CANCEL_ORDER and 12 more, with catalog IDs. Code turns events into the order. VersionEach send of one order. v1 is order.finalized; corrections are order.updated. OutboxThe table every webhook is written to before sending, so nothing is lost on a crash. Dead letterA delivery that failed every retry (about a day). Resend from the UI or CLI. ReviewThe flag that says a person should check this order, with reasons. Independent of status. PlaceholderA value we invented until Serv or HME provides the real one; flagged on every order. FixtureA scripted test conversation with a known right answer. E1 to E12The v2.1 decisions, listed in the README.
